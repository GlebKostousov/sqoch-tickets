# Решения по тестовому

## Объём

Задание требует рабочий интерфейс оформления на моковых данных. В проекте один пользовательский сценарий: ввод участников и контакта, проверка состава и суммы, подтверждение и результат. Событие и его описание — демонстрационные данные.

Использован frontend-стек ТАКТ: SvelteKit, Svelte 5 и TypeScript в строгом режиме. Результат собирается в статические файлы. Backend, авторизация и база данных для заданного сценария не нужны.

## Слои и состояние

Чистые функции отвечают за возрастные правила, допустимый состав заказа и стоимость. Компоненты отвечают за ввод, доступность и представление ошибок. Gateway представляет источник данных и результат подтверждения. Состояние конкретного оформления принадлежит его экземпляру.

Страница подключает компоненты и зависимости через публичный модуль сценария оформления. Правила заказа и работа с источником данных остаются внутри этого модуля.

Полный query/entity/realtime data plane ТАКТ не перенесён: здесь нет общей серверной сессии, нескольких организаций, кэша списков и обновлений от других пользователей. Типизированный gateway и явные переходы между шагами покрывают имеющийся объём. Добавлять общий кэш без потребителя было бы лишней обязанностью поддержки.

## Правила, которые легко перепутать

| Правило                    | Решение                                                                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Граница детского тарифа    | Возраст меньше 14 лет                                                                                                      |
| Граница полного тарифа     | Возраст от 14 лет включительно                                                                                             |
| Сопровождающий             | Участник от 18 лет в том же заказе                                                                                         |
| Подросток 14–17 лет        | Полный билет, самостоятельное посещение допустимо; сопровождать ребёнка нельзя                                             |
| Взрослый и несколько детей | Допустимо, если общее количество участников не больше четырёх; отдельный взрослый на каждого ребёнка не требуется заданием |
| Возраст                    | Целое число от 0 до 120; верхняя граница — допущение формы                                                                 |
| Стоимость                  | Целые рубли, без вычислений с дробными денежными значениями                                                                |

Сопровождение проверяется по составу всего заказа. Удаление взрослого или изменение его возраста должно снова сделать заказ с ребёнком недопустимым.

## Подтверждение и отсутствие мест

Цена на экране получается из текущих участников. На шаге проверки пользователь видит те данные, которые собирается подтвердить. Возврат к форме сохраняет ввод; изменения приводят к новому расчёту.

Наличие мест решается при финальном подтверждении через gateway. Параметр `?scenario=sold-out` делает этот исход воспроизводимым. Сценарий не подменяется ранней ошибкой валидации: пользователь сначала проходит обычные шаги оформления.

Во время запроса кнопка подтверждения не запускает ещё один заказ. Успешное оформление показывает результат mock-системы; интерфейс не утверждает, что деньги списаны или письмо действительно отправлено. При отказе форма сохраняется, причина объясняется обычным языком.

Gateway повторно проверяет полученные данные и пересчитывает сумму. Для одного ключа запроса и одинакового состава он возвращает тот же результат; повторное использование ключа с изменёнными данными даёт типизированную ошибку. Эти свойства действуют внутри одного экземпляра mock gateway. Хранения заказов после перезагрузки и межвкладочной координации нет.

Для реальной продажи проверка остатка и создание заказа должны выполняться на сервере атомарно. Клиентская блокировка кнопки сама по себе не защищает от двух вкладок или параллельных покупателей. Финальная цена также должна пересчитываться на сервере.

## Персональные данные

Имена и контактный email находятся только в памяти экземпляра приложения. Их не нужно сохранять в `localStorage` ради демонстрации. После перезагрузки ввод теряется: это заявленное ограничение mock-версии. В ТАКТ долговременное восстановление персональных данных требует серверного черновика.

В интерфейсе и документации не обещается отправка письма: email собирается как поле заказа, отправка не реализована. Никакие реальные персональные данные для проверки не нужны.

## Проверка качества

TypeScript и `svelte-check` проверяют контракты и компоненты. ESLint и Prettier держат единый стиль. Страж импортов держит страницу тонкой и закрывает внутренние файлы пакета снаружи. Unit-тесты защищают бизнес-границы, браузерные проверки проходят пользовательские шаги и размер экрана 360 px.

Приёмка покрывает успешный заказ, ребёнка без взрослого, подростка в роли сопровождающего, удаление взрослого, ограничение количества, возврат к редактированию, пересчёт цены и отсутствие мест при подтверждении.

Все перечисленные сценарии покрыты. Итог: 54 unit/state-теста и 28 браузерных проверок (14 сценариев на двух размерах экрана). Готовая статическая сборка отдельно прошла четыре проверки: успех и отсутствие мест на desktop и 360 px. Фактический вывод сохранён в `verification.txt` и `browser-verification.txt`.

Браузерные тесты выявили потерю ввода до гидратации. Форма теперь включается после `onMount`; отдельный тест задерживает загрузку JavaScript и проверяет отсутствие потери данных. При повторе после неизвестного результата ключ сохраняется даже после возврата к форме, если нормализованный состав не изменился. Имена, email и суммы в ошибку и журналы приложения не передаются.

## Выбор инструментов

Из ТАКТ использованы подходы к организации frontend-кода: строгий TypeScript, отдельные правила заказа, явные зависимости и тесты. Серверные модули ТАКТ в проект не переносились.

Для установки зависимостей выбран npm. Файл `package-lock.json` фиксирует версии, поэтому получателю достаточно Node.js и команды `npm ci`.
